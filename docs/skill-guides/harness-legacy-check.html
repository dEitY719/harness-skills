01 — Scope

언제 쓰고, 언제 안 쓰는가

ai-context check 가 문서 한 개를 보는 데 비해, 이 스킬은 하네스 전체를 본다. 둘 다 읽기 전용이라는 점은 같다.

사용

하네스 전반에 쌓인 legacy 규칙·중복·비대화를 훑고 싶다.

사용

harness:harness-refactor 를 돌리기 직전. 이 감사가 refactor 의 입력을 만든다.

금지

감사 결과를 적용하고 싶다. 대신 harness:harness-refactor

금지

컨텍스트 문서 한 개만 점검하고 싶다. 대신 harness:ai-context check

금지

저장소 디렉터리 구조만 본다. 대신 packaging:structure-check

03 — Skill behaviour

스킬이 하는 일은 세 가지

스킬 자체는 호출과 완료 보고가 전부다. 실제 분석은 워크플로우 안의 에이전트들이 수행한다.

1

워크플로우 실행

Workflow({ name: 'harness-legacy-check' }) 를 한 번 호출한다.

2

리포트 저장

완료되면 .claude/reports/harness-legacy-check.md 에 리포트가 저장된다 (덮어쓰기).

3

완료 보고

[OK] harness:harness-legacy-check — 완료 와 리포트 경로, 다음 단계 /harness:harness-refactor 를 출력한다. 실패 시 [FAIL] … — <이유> 를 출력하고 즉시 중단한다.

04 — Workflow

워크플로우 5-phase 파이프라인

무거운 일은 전부 여기서 일어난다. 수집 → 병렬 분석 → 계획 → 자기반박 → 리포트.

각 phase 를 눌러 상세를 펼친다.

CLAUDE.md, AGENTS.md, skills, workflows, settings, hooks, MCP — 하네스를 구성하는 자산을 빠짐없이 목록화한다. 이후 phase 는 전부 이 목록 위에서 돈다.

다섯 개의 전문 에이전트가 동시에 붙어 각자 영역을 분석한다. 이 병렬 구간이 토큰 비용의 대부분을 차지한다.

분석 결과를 항목별 처분으로 환산한다. 이 분류가 그대로 harness:harness-refactor 의 작업 목록이 된다.

KEEP SHRINK MOVE SPLIT CONVERT DELETE

계획을 그대로 통과시키지 않는다. 각 DELETE·SHRINK 제안에 대해 "이걸 잘라내면 무엇이 깨지는가"를 반대편에서 따진다. 과감한 감사와 안전한 결과를 동시에 얻기 위한 장치다.

살아남은 findings 를 .claude/reports/harness-legacy-check.md 한 파일에 정리한다. 이 스킬이 저장소에 남기는 흔적은 이것뿐이다.

05 — Constraints

주의사항 / 제약

실행 전에 알고 있어야 할 네 가지.

파일을 수정·삭제하지 않는다

유일한 쓰기는 리포트 파일 생성이다. 감사 결과의 적용은 이 스킬의 일이 아니다.

리포트는 매 실행마다 덮어쓰기

이전 리포트를 보존하려면 실행 전에 따로 복사해 두어야 한다.

Claude Code Workflow 도구 의존

실행되지 않으면 /config 에서 Dynamic workflows 와 Ultracode keyword trigger 가 모두 true 인지 확인한다. 다른 하네스에서는 references/*-tools.md 의 대체 경로를 따른다.

토큰 비용이 작지 않다

워크플로우가 다수의 에이전트를 띄운다. 가볍게 반복 호출할 스킬이 아니다.

06 — Pairing

refactor 와 한 쌍

저장된 리포트가 그대로 refactor 의 입력이 된다.

harness:harness-legacy-check 읽기 전용 감사 · 리포트 산출
→
harness:harness-refactor 리포트의 low-risk findings 적용
